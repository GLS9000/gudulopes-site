# Site review — 22 October 2026

_Audit of the Gudu Lopes site (**gudulopes.com**), covering every issue found,
which ones were fixed on the spot, and which are still open. Written to be
readable by someone who has never seen this project: if you are new here, read
`START-HERE_context.md` first (project background, how the owner works, live
deployment reality), then `HANDOFF.md` (file structure, editing, deploy steps).
This file is the audit; `HANDOFF.md` §11 holds the running changelog._

**What was reviewed:** the `v3` folder as supplied by the owner (file dates 24–25
July 2026) —
`index.html`, `four-doors.html`, the four door pages, `boku-no-sekai.html`,
`404.html`, `css/style.css`, `js/script.js`, and the contents of `assets/`.
Reviewed as source code, not as a rendered live page.

**Version produced:** v3.3.

---

## 1. Verdict

The site is soundly built. It is a genuinely static, no-build-step site — plain
HTML, one stylesheet, one small script — which is exactly right for GitHub Pages
free tier and for an owner who edits in VS Code and GitHub Desktop. The things
that are easy to get wrong were already right:

- Semantic HTML: real `<nav>`, `<main>`, `<header>`, `<article>`, `<footer>`.
- Accessibility groundwork: skip link, visible `:focus-visible` outlines,
  `aria-current` on the active nav item, `aria-label` on the menu button with
  `aria-expanded` kept in sync by the script, `aria-hidden` on decorative
  imagery, `prefers-reduced-motion` respected.
- Performance groundwork: `width`/`height` on every image so nothing shifts
  while loading, `loading="lazy"` below the fold, `fetchpriority="high"` on the
  hero, WebP where it matters.
- Privacy: fonts self-hosted from `assets/fonts/` (no request to Google, so no
  GDPR question), and all YouTube embeds on `youtube-nocookie.com`.
- Findability: canonical URLs, Open Graph tags, `sitemap.xml`, `robots.txt`,
  and `MusicGroup` JSON-LD with every streaming profile in `sameAs`.
- An on-brand `404.html`, and a mobile deep-link script that opens the native
  Spotify / Apple Music app instead of the mobile web player.
- `<!-- EDIT: ... -->` comments marking every spot the owner is expected to
  change, which is what makes the site genuinely self-maintainable.

The issues below are specific defects and gaps, not structural problems. Nothing
found here calls for a rebuild.

## 2. Findings — fixed in v3.3

### 2.1 CRITICAL — six broken video embeds were live

`door-of-madness.html` (2 songs) and `door-of-death.html` (4 songs) still
contained the scaffold value:

```
<iframe src="https://www.youtube-nocookie.com/embed/VIDEO_ID" ...>
```

`VIDEO_ID` is not a real YouTube ID, so each one rendered as a black box reading
"Video unavailable." Those two pages read as broken rather than as
work-in-progress.

**Fix applied.** Each placeholder `<div class="video-container">…</div>` and its
comment was replaced with a commented-out one-line template:

```html
<!-- EDIT: VIDEO — no video for this song yet. When there is one,
     paste this line here and swap PASTE_ID for the YouTube ID
     (the part after v= in the watch URL):
<div class="video-container"><iframe src="https://www.youtube-nocookie.com/embed/PASTE_ID" title="Song title" loading="lazy" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture" allowfullscreen></iframe></div>
-->
```

Nothing was lost: the tracklist at the top of each page and the "Still to come"
block already communicate which songs exist. The markup to restore is inline, so
adding a video later is still a paste-and-swap job.

**Rule going forward:** never leave a placeholder inside a live `src`. An absent
element is invisible; a broken embed is loud.

### 2.2 CRITICAL — four font files were declared but missing

`css/style.css` declared seven `@font-face` rules, but `assets/fonts/` contained
only three files. Missing: `cinzel-700.woff2`, `lato-300.woff2`,
`lato-400italic.woff2`, `lato-700italic.woff2`.

Two consequences: every page load fired four 404 requests, and any italic text
— `<em>Rapperz van de Ronde Tafel</em>` in the homepage bio, `<em>Kompas</em>`
and `<em>Boku no Sekai</em>` on the Boku page — fell back to a system italic
that does not match Lato, so the typeface visibly changed mid-sentence.

**Fix applied.** The four rules for absent files were removed. Only the three
faces that exist are declared (`cinzel-400`, `lato-400`, `lato-700`); the browser
now synthesises italics and bold display text from them, which keeps the type
consistent.

**If you want the real cuts later:** download `Cinzel` 700 and `Lato` 300 /
400-italic / 700-italic as `.woff2`, drop them in `assets/fonts/`, and restore
the matching `@font-face` lines in the same format as the existing three. A true
italic cut is better than a synthesised slant — this is a quality upgrade, not a
bug fix.

### 2.3 SHOULD FIX — 854 KB of unreferenced images

`assets/images/` held `gudu-portrait.png` (706 KB) and `gudu-portrait.jpg`
(148 KB). Nothing in any HTML file referenced either; only `gudu-portrait.webp`
(69 KB) is used. They were leftovers from producing the WebP.

**Fix applied.** Both deleted. The image folder went from roughly 1.7 MB to
848 KB.

Worth knowing: because this is a git repo, the bytes remain in history — the
working folder is lighter, but the clone size barely moves. That is fine and not
worth rewriting history over. The point of the deletion is to stop confusing
whoever edits next about which portrait is the live one.

### 2.4 Track title corrected in the notes

`START-HERE_context.md` listed Door of Sleep track 6 as "Lullaby" while the site
showed "In Loving Arms". **Confirmed by the owner: the correct title is
"In Loving Arms."** The site was already right; the notes were stale and have
been corrected.

### 2.5 Housekeeping

The stylesheet cache-buster was bumped from `style.css?v=12` to `?v=13` across
all pages, so returning visitors get the edited CSS rather than a cached copy.
**Bump this every time `style.css` changes** — it is a find-and-replace across
the `.html` files.

## 3. Feature added in v3.3 — the premiere / announcement bar

The owner asked where to put a YouTube Premiere link. Two places, for two
different reasons.

### 3.1 The bar (added)

A new `<aside class="premiere-bar">` sits at the very top of `index.html`, above
the `<nav>`, with matching `.premiere-bar` rules in `css/style.css` built from
the existing colour tokens (`--bg-elevated`, `--line`, `--accent`, `--text`). It
wraps to two lines on narrow screens. The nav is `position: relative`, not
sticky, so placing the bar above it needs no layout compensation.

It is at the top because a premiere is the one piece of time-sensitive content on
an otherwise evergreen page: it must be visible before any scrolling, and it must
carry a date. The link points at the plain YouTube watch URL, because the
"Notify me" button that actually captures interest lives on YouTube's own
countdown page — an embed alone cannot capture it.

**⚠️ It ships with placeholders.** `[DAY DATE], [TIME] CEST` in the text and
`PREMIERE_ID` in the link. Fill both in, or delete the whole `<aside>` block,
before pushing — otherwise the placeholder text goes live.

**After the event:** delete the `<aside>` from `index.html`. Leave the CSS; the
next premiere only needs the HTML block back. Copy the block to other pages only
if traffic is being driven to them directly.

Include a timezone in the text. The audience is not all in Belgium, and "20:00"
alone is ambiguous.

### 3.2 The homepage "Watch" embed (documented, not changed)

A premiere's video ID works in an ordinary embed: before the premiere the box
shows YouTube's countdown, and afterwards it becomes the finished video with
nothing to change back. So the premiere ID can go straight into the existing
`Watch` iframe on `index.html`, and the empty caption `<p>` directly beneath it
is where the date line belongs.

This was documented as a comment in `index.html` rather than applied, because
the `Watch` section currently holds a working video and swapping in a
placeholder ID would have recreated exactly the defect fixed in §2.1.

### 3.3 Bonus

If the premiering track belongs to a specific door, paste the same ID into that
song's iframe on the door page. That promotes the premiere and fills one of the
gaps from §2.1 in a single edit.

### 3.4 The recurring release workflow (confirmed by the owner)

The homepage `Watch` section is the **"Latest release" slot: a rotating window
that holds exactly one video.** After a premiere ends, that video is what belongs
there. The door pages are the permanent home for every video.

That distinction matters, because it produces one step people forget. Per
release:

1. **When the premiere is scheduled** — paste the video ID into the `Watch`
   iframe on `index.html`, and into the premiere bar link. The embed shows
   YouTube's countdown until the premiere, then becomes the video by itself.
2. **After the premiere** — delete the `<aside>` premiere bar. Update the caption
   `<p>` under the video to the song title. The embed needs no change; it is
   already the finished video, and it is now the latest release.
3. **Also paste the same ID into that song's slot on its door page** — using the
   commented one-line template left there in v3.3.

**Step 3 is the one that gets skipped, and it is the one that loses work.** The
`Watch` slot holds one video: the moment the *next* premiere takes it, the
previous video is gone from the homepage. If it was never added to its door page,
it disappears from the site entirely while remaining perfectly fine on YouTube —
easy to miss, because nothing breaks.

Done correctly, every video ends up in two places: temporarily on the homepage as
the latest release, permanently on its door page in tracklist order. The current
state is a good example — the homepage `Watch` embed and *Contemplation* on
`door-of-forgetting.html` both point at the same ID, which is exactly right.

One thing outside your control: the embed draws YouTube's own title overlay
across the top of the box, and a long title gets clipped mid-word. There is no
supported parameter to hide it (`showinfo` was removed in 2018). This is why the
caption `<p>` beneath the box is worth filling in — it is the only clean,
readable title you control on that section.

## 4. Still open — needs the owner's input or assets

Ordered by impact.

### 4.1 `og-image.png` is still a text-only placeholder

`assets/images/og-image.png` is the branded text card, and it is what
`index.html`, `four-doors.html` and the door pages hand to WhatsApp, Facebook,
Discord and every other platform that unfurls a link. Every share of the
homepage currently shows a generic card instead of a photograph.

This is the highest-leverage single fix available, and it matters most in the
run-up to a premiere, when links get shared. **Needs: one real image, 1200×630.**
The Sleep and Boku pages already override this with their real cover art, so
only the homepage and the hub pages are affected.

### 4.2 No streaming buttons on any Door page

`boku-no-sekai.html` has a `listen-actions` block with Spotify and Apple Music
buttons. None of the four door pages has one. *Door of Sleep* is a finished
album with no way to stream it from its own page — a visitor who reads about it
has to navigate back to the homepage to listen.

**Fix:** copy the `<div class="listen-actions">…</div>` block from
`boku-no-sekai.html` into each door page's `album-head` section and swap the
album URLs. The CSS already exists. **Needs: the per-album Spotify / Apple
Music URLs.**

### 4.3 Song stories are all empty

Every `<div class="track-story"></div>` on every door page is blank. Given that
the whole premise of *Four Doors of the Mind* is storytelling — love, loss,
longing, fantasy and sci-fi threaded through four thresholds — this is the
site's biggest missed opportunity, and no amount of design substitutes for it.
It is also the content most likely to make someone stay on the page.

**Needs: the owner writing prose.** Nothing technical blocks it — one paragraph
per song, inside the existing `<div>`.

### 4.4 Cover art missing for three doors

`forgetting-cover.jpg`, `madness-cover.jpg` and `death-cover.jpg` do not exist
yet, so those pages fall back to the text "cover-fallback" block. (The
`onerror="this.remove()"` attribute on the `<img>` handles the absence cleanly —
this is intentional, not a bug.) **Needs: square art, optimised per §5.**

### 4.5 The homepage "Watch" caption is empty

The `<p>` under the video is blank, so the section says "Latest release / Watch"
without naming what is playing. The embedded video is currently the same one used
for *Contemplation* on `door-of-forgetting.html`. Worth a line: song title, and
which door it belongs to.

### 4.6 Nice-to-have: album structured data

`index.html` carries `MusicGroup` JSON-LD. The album pages carry none. Adding a
`MusicAlbum` block per door page (album name, `byArtist`, track names) is a cheap
way to help search engines understand the tracklists. Low urgency, real payoff
once the albums are released.

## 5. Reference — image optimisation

Before adding any image, resize it. Source files from phones, cameras and image
generators are far too heavy for a free-tier static site; the original covers
arrived at 3780×3780 and 1–3 MB.

| Purpose | Target size | Format & quality |
| --- | --- | --- |
| Square cover art | 1000×1000 | JPEG q≈82, progressive |
| Social share (`og-image`) | 1200×630 | PNG or JPEG |
| Portraits / banners | max ~1800 px on the long edge | WebP q≈80 |

Aim well under 300 KB per file. For reference: Sleep's cover went 2.9 MB → 224 KB
and Kompas 1.1 MB → 62 KB at those settings, with no visible loss.

Keep an eye on the total. The site is around 1.1 MB including documentation,
which is comfortable — GitHub Pages free tier has a soft 1 GB repository limit
and 100 GB/month of bandwidth, so the practical concern is load speed on a phone
rather than the quota.

## 6. Known limitations of the current architecture

Not defects — consequences of the no-build-step decision, which is the right
call here. Recorded so nobody is surprised.

- **The nav and footer are duplicated in all eight HTML files.** Changing a nav
  link means editing eight files. This is the price of having no build step, and
  it is worth paying at this size. Use "find in all files" (`Ctrl+Shift+F` in
  VS Code) rather than editing one and hoping. If the site ever passes roughly
  fifteen pages, revisit — but revisiting means introducing a build step, which
  would end web-editor editing, so the bar should be high.
- **No mailing list, store, or booking form.** GitHub Pages serves static files
  and cannot process a form submission. Any of these needs a third-party embed
  (e.g. a hosted form or mailing-list provider). Deliberately deferred.
- **No analytics.** Nothing currently records visits. Same constraint: it would
  need a third-party script, with the privacy tradeoff that implies.
- **Printing the site looks broken.** Browsers do not print background colours,
  so the dark theme prints as near-invisible text. A print artifact, not a bug.
  A print stylesheet could fix it if it ever matters.
